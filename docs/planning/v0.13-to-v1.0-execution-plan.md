# v0.13 to v1.0 execution plan

Status: **Maintained coordination plan** (2026-08-19). Keep this document
current until `v1.0.0` is published, then mark it complete rather than
rewriting it as architecture or release history.

The [roadmap](../roadmap.md) owns released and release-gated scope. The
[release process](../releasing.md) owns exact-SHA release mechanics. Maintained
architecture documents own current behavior. The
[pathfinding prototype survey](pathfinding-prototype-survey-2026-08-18.md) is a
point-in-time research input, while the
[strategy comparison](../pathfinding-strategy-comparison.md) supplies maintained
adopter guidance. This plan supersedes the survey's ordering and status
assumptions where later evidence or decisions differ.

## Outcome

The remaining route to 1.0 has four phases:

1. graduate the maintenance API and publish it in `v0.13.0`;
2. after `v0.13.0`, disposition the complete bounded prototype queue;
3. evaluate the resulting source surface in a substantial downstream, then
   publish and observe `v1.0.0-rc.1`; and
4. publish `v1.0.0` only after the observation and exact-SHA release gates.

Maintenance graduation is a `v0.13.0` release blocker. Prototype
investigations after 0.13 may accept, reject, or defer a candidate; completing
the bounded investigation and recording its disposition is the pre-RC gate,
not forcing every candidate into production.

## Rules shared by every prototype PR

Each investigation begins with a bounded issue or PR description that fixes:

- one hypothesis and the smallest private implementation that can test it;
- the canonical baseline, an interleaved control, and an independent
  correctness oracle;
- metrics and a noise-derived go/no-go threshold declared before results;
- determinism, allocation, memory, version, invalidation, ownership, and
  failure contracts;
- the raw evidence location, stop condition, and reconsideration condition;
  and
- source revisions and license compatibility before copying code or fixtures.

Tests precede implementation. A correctness, contract, determinism, lifetime,
or allocation failure may stop an experiment before timing both platforms.
Passing tests establish only the properties their independent oracle observes;
they do not turn a microbenchmark or call count into an end-to-end claim.

Completed experiments add one optimization-log fragment whether accepted,
rejected, or deferred. Accepted behavior updates maintained architecture; a
material authority decision adds a decision fragment; a user-visible change
adds a release fragment. PR X2 records candidates excluded from the queue by
an existing authority boundary. PR X3 records unopened conditional queue
members. Neither receives a speculative experiment fragment.

Keep prototypes private until evidence justifies authority. Accepted code must
land before downstream evaluation. Rejected code is removed from the branch;
the retained artifact is the evidence record, not dead production machinery.

### Cross-hardware decision rule

For a portable performance change, accept when at least one controlled
platform materially wins and neither materially regresses. Reject when either
platform materially regresses. Record a flat result explicitly. Hardware-
specialized production paths are outside this plan and require a separate
decision.

Use paired, interleaved A/B runs on the M3 and Steam Deck with separate
noise-derived thresholds. Never compare absolute times across machines. A
performance-only rejection is not final until both platforms run. The M3 and
Deck legs of one frozen candidate may run in parallel, but campaigns on each
physical device serialize with every other candidate using that device.

One-off controlled campaigns may decide whether a candidate is accepted for a
release. Permanent hosted-CI timing gates remain advisory until representative
baseline history establishes sensitivity and tolerable false-positive rates.

## Phase 1: maintenance and v0.13

The maintenance PRs are sequential because each fixes the contract used by the
next. No Phase 2 PR begins before `v0.13.0` is published.

### PR MNT-1: stable contract candidate

Starting from the merged failure-diagnostics contract, revise the experimental
API under tests before granting it stable authority.

- Add an opaque maintenance handle and define owner, registration epoch,
  validity, stale-handle, move, release, and destruction behavior.
- Prefer a fixed registered-task model matching the selected dirty-bit
  backend. Adapter-owned stable slots, rather than chunk-owned task pointers,
  make sparse slot reuse representable without post-seal registry mutation.
- Replace conflated boolean outcomes with explicit schedule and drain results
  for recoverable operational states. Callers must be able to distinguish
  retryable capacity, idle completion, budget exhaustion with pending work,
  zero-progress stall, and task failure where exceptions are enabled.
- Follow the merged failure-diagnostics boundary for invalid setup and
  identity. Unsafe lifecycle or ownership misuse, including detectable use
  through the wrong scheduler or registration epoch, fails fast in every
  build. Where stale-handle uncertainty is an expected caller condition,
  provide a checked operation rather than manufacturing a normal-looking
  schedule or drain result.
- Preserve explicit flush points, deterministic registration order,
  non-self-concurrent execution, and allocation-free warmed scheduling.
- Keep exact events, commands, saves, combat, economy, and authoritative
  simulation mutation outside maintenance.
- Keep FIFO and queued-coalescing backends experimental comparison machinery.
  The unconditional stable candidate consists only of the shared
  task/budget/result contract, immediate execution, handles, the adapter
  boundary, and diagnostics needed by consumers. Dirty-bit graduation is
  conditional on MNT-3's portable-performance gate.

Test checked stale-handle paths and fail-fast handle misuse in both diagnostic
and assertion-disabled configurations, including wrong scheduler or epoch,
task and scheduler destruction, and repeated release. Also test pending work,
concurrent producers and drains, reentrancy, exceptions, zero progress,
capacity boundaries, and exception-free behavior. Record the intentional
divergence from any historical TDD wording once the tested contract is settled.

### PR MNT-2: external chunk adapter

Build the first real consumer of the MNT-1 contract while it is still
experimental.

- Keep ownership external to `World` and `ChunkMeta`; do not change world
  construction or embed scheduler handles in authoritative storage.
- For dense worlds, bind stable adapter slots to chunks. For sparse worlds,
  bind stable slots to resident capacity and change a slot's chunk binding only
  at a quiescent boundary with a new residency generation.
- Drive mark, observe, rebuild, generation-safe clear, retry, budgeted
  continuation, flush, release, eviction, reload, and slot-reuse paths.
- Demonstrate one real derived product and preserve byte-identical
  authoritative archives across immediate and dirty-bit backends.
- Add a compiled installed-package example showing dirty/version inspection;
  no example may imply one execution per schedule call.

The adapter must work for dense and sparse residency or explicitly fail the
stable promotion gate. Narrowing the stable claim to dense only is not an
implicit fallback; it requires a new decision because the adapter and handle
shape would otherwise freeze before sparse lifecycle pressure is understood.

### PR MNT-3: promotion evidence

Freeze the MNT-2 candidate and collect correctness evidence before timing.

- Repeat deterministic 1,000-run flush, canonical archive equivalence,
  generation-safe clear, exception, shutdown, allocation, ASan/UBSan, and TSan
  evidence against the adapter rather than only synthetic tasks.
- Run sparse, dense, mixed, flush, budgeted, and task-count scaling controls on
  the M3 and Steam Deck. The two device legs may run in parallel.
- Compare the adapter with immediate, FIFO, and queued-coalescing controls.
  Promote the dirty-bit implementation only if it materially wins on at least
  one platform without a material regression on the other.
- Record environment, binary SHAs, order randomization, repetitions,
  uncertainty, raw artifacts, memory, allocations, and work counters.
- Calibrate Linux main-tier thresholds only when enough representative
  artifacts exist. Otherwise keep them honestly advisory and use the retained
  controlled campaign as the 0.13 promotion decision.

A failed contract gate returns to MNT-1 or MNT-2 and then reruns MNT-3. A flat
cross-platform performance result still permits the stable task, handle,
result, adapter, and immediate-execution contract to graduate, but keeps the
dirty-bit implementation experimental and records the flat disposition. A
material dirty-bit regression also keeps that backend experimental. Stable
maintenance is selected for 0.13; contract failure delays the release, while a
performance-only backend result does not deadlock it.

### PR MNT-4: graduation

After MNT-3 passes:

- move the accepted surface to `include/tess/maintenance/` and
  `tess::maintenance`, with narrow headers preferred over one monolith;
- classify those headers as stable and choose aggregate membership
  deliberately;
- leave FIFO and queued-coalescing implementations under
  `tess::experimental`, and leave dirty-bit there too unless MNT-3 passes its
  portable-performance gate, while reusing stable task and result types where
  useful;
- add stable installed, FetchContent, exception-free, no-RTTI, compiler-floor,
  and portable-header consumers;
- update Doxygen, architecture, integration policy, support policy, roadmap,
  upgrade guide, examples, surface inventory, changelog, and decision records;
  and
- run the full supported test matrix with all maintenance-specific sanitizer
  and concurrency cells.

Before merging, provide the exact MNT-4 candidate to a focused downstream
maintenance tryout. Exercise registration, handles, sparse lifecycle, budgeted
drains, flush points, shutdown, and upgrade ergonomics; resolve every
source-contract finding and rerun affected evidence on the final head. This is
a narrow pre-0.13 risk check, not the later substantial whole-surface
evaluation.

The stable source contract includes documented names and semantics, not ABI,
object layout, mixed tess versions, or cross-DSO identity beyond the existing
support policy.

### PR REL-13: publish v0.13.0

After MNT-4 and every other accepted 0.13 change land:

- preview changelog, decision, and optimization-log assembly transactionally;
- token-count all release-written logs and archive assembled history before a
  file would exceed 24,000 tokens;
- assemble the three fragment streams for `0.13.0` and verify no fragment or
  unreleased entry is lost;
- set and verify the final version and upgrade documentation;
- run release mode against the exact release SHA; and
- publish only the portable archives and checksums produced by that successful
  run.

## Phase 2: post-0.13 prototype queue

The path-core stream is serialized because its candidates alter or measure the
same search internals. The movement stream is separately serialized because
its candidates share fixtures and later experiments require a pinned final
policy. The execution harness is independent of both streams' internal
ordering, but still starts after 0.13. These streams may run in parallel with
each other subject to the shared hardware queue.

### Serialized path-core stream

#### PR P1: residual portal-seam screen

Profile the post-PR-213 implementation and measure cost-weighted residual seam
work at the end-to-end portal tick. Implement a private seam-local index only
if the residual profile leaves a material removable-cost hypothesis.

Require exact equivalence for empty, tied, edited, sparse-residency, diagonal,
hex, and provider-composed cases; correct topology and version invalidation;
bounded bytes and allocations; and a material end-to-end win. Run performance
evidence on both M3 and Deck. A memo-local win or stale pre-#213 profile is not
acceptance evidence.

#### PR P2: resumable and cancellable A* screen

Use caller-owned private state and one expansion as the deterministic work
unit. Pin contiguous-versus-resumed cost and route validity, cancellation,
staleness, content-version, memory, lifetime, allocation, and deterministic
pause/resume behavior for unit and weighted search.

This PR answers semantic feasibility and measured scheduling value; it stops
before inventing a broad public continuation framework. Semantic rejection
does not need two-platform timing. Any performance claim does.

#### PR P3: gated JPS specialization

Admit only resident dense regular 2D, symmetric uniform-cost movement with no
provider or custom transitions. Use generated in-repository maps unless rights
for an external fixture are documented. Compare open, wall-gap, maze, and
rubble shapes against current exact A* with an independent validity and cost
oracle.

Reject if the capability gate becomes complicated, exactness fails, median
eligible workloads regress, or ineligible callers can enter the path. Final
performance evidence requires M3 and Deck.

#### PR P4: whole-query bidirectional A* screen

Keep this screen whole-query-only; do not combine it with resumable state.
Restrict it to the resident dense regular 2D, symmetric unit-cost subset of
P3's uniform-cost domain.
Require optimal cost parity, independently valid routes, deterministic
bidirectional results, bounded memory, and correct fallback.

Route identity with unidirectional A* is not required. If P3 is accepted, JPS
is the performance incumbent on their shared eligible domain; otherwise A* is
the incumbent. Run final performance evidence on M3 and Deck.

#### PR P5: D* Lite incremental-replanning screen

Pre-register edit locality, edit frequency, map size, query reuse, and the
minimum movement-cost floor that preserves heuristic admissibility under cost
decreases. Replay each edit sequence deterministically and compare every answer
with fresh canonical search using validity and cost oracles.

Gate feasibility first on deterministic work ratios, counters, allocations,
memory, and invalidation. Wall time becomes final only on M3 and Deck. Include
a synthetic churn trace; any trace derived from the congestion experiment is
supplemental and cannot decide acceptance.

#### PR P6: conditional priority-queue retry

Do not rerun the rejected four-ary heap unchanged. Open this PR only if P2-P5
introduce a structurally different open set, D* Lite exposes a materially
different priority-queue pattern, or a new profile meets the recorded retry
condition. Carry forward the differential pop-order oracle and per-consumer
goldens. Require M3 and Deck non-regression.

### Serialized movement and scenario stream

#### PR C1: PIBT hindrance tie-break

Preserve route attachment as the primary rank and apply hindrance only among
equal-rank candidates before deterministic enumeration. Require terminal
parity, deterministic replay, route validity, no warm allocation regression,
and a pre-registered quality win across warehouse, ring, colony, random, and
adversarial fixtures. Tick-cost acceptance requires M3 and Deck. Accepted
behavior receives release and architecture documentation even without a new
public API.

#### PR C2: explicitly fungible goals

Prototype target reassignment only when the caller supplies an anonymous goal
set. Never infer fungibility from individually assigned goals, and preserve
identity-sensitive accounting. Require assignment validity, determinism,
terminal parity, bounded memory, and a quality or throughput win. Use both
hardware platforms if performance contributes to acceptance.

#### PR C3: reciprocal-conflict fixture and current-tier screen

Construct a reproducible reciprocal conflict and run canonical seeded routing,
joint movement, and the final C1 PIBT policy. Use a tiny optimal solver only as
an oracle. If the existing tiers solve the fixture within the pre-registered
bound, record that result and do not open C4.

#### PR C4: conditional conflict-local temporal escalation

Open only when C3 proves a failing fixture. Plan only the affected conflict
component, preserve canonical behavior elsewhere, and compare with the tiny
optimal oracle. Do not introduce a global fixed-horizon planner, WHCA, CBS, or
LaCAM. Include fixtures whose conflict queues exceed any bounded candidate
horizon so the prior WHCA failure mode cannot be hidden. Use both hardware
platforms when runtime or throughput contributes to acceptance.

#### PR C5: dynamic congestion revalidation

Run only after C1-C4 settle the canonical movement tier. Rebaseline on the
corrected cross-cut topology; prior arrival and wait numbers are context, not
the control. Revalidate one bounded dynamic-price policy, not a general
congestion-field design, and include the topology-edit replay with pricing
active.

Require every supported population to retain the same terminal classification
and failure counts no worse than canonical. Recurrence of either prior
incomplete arrivals or crowd-blocked outcomes reconfirms rejection and stops
the experiment. Measure performance on M3 and Deck if it forms any part of the
case.

#### PR C6: conditional capacity-aware crossing reservation

Do not rerun equal-cohort balanced waypoints. Open only if C3-C5 isolate a
capacity-contention premise that a bounded crossing reservation or flow rule
can represent. Preserve terminal outcomes and reject synchronized hotspot
creation. Without that changed premise, disposition the idea without a run in
PR X3.

### Independent and synthesis stream

#### PR X1: execution-delay and uncertainty harness

Build a private harness that injects delayed completion and compares
synchronous plans, request/move/release states, and explicit action-dependency
edges. Measure collisions, deadlocks, throughput, recovery, determinism, and
accounting. The harness decides whether a new execution contract is justified;
it does not grant one. Use both platforms only if timing affects the decision.

#### PR X2: authority-boundary dispositions

Record, without speculative implementation:

- clearance/radius products remain post-1.0 because capability-specific
  topology changes caching, invalidation, and movement-class semantics;
- Theta* remains deferred until line-of-sight, smoothing, timing, and
  route-validity contracts exist;
- fixed-horizon WHCA remains superseded by the C3/C4 conflict-local gate.

PR X3 records whether P6 and C6's retry conditions occurred. If they did not,
the existing four-ary-heap and balanced-waypoint rejections remain in force
without a new experiment.

#### PR X3: prototype synthesis

After every required run or no-run disposition:

- list each candidate, evidence record, outcome, limitations, and
  reconsideration condition;
- confirm every accepted implementation and required maintained-doc update has
  landed;
- distinguish private optimization, supported behavior, public API, deferred
  research, and rejected mechanism;
- preview and token-count the accumulated fragment assembly, archiving logs if
  needed; and
- update the roadmap from the outcomes without rewriting the historical survey
  as current architecture.

Serialize X3 with any other PR editing the roadmap or release-facing records.

## Phase 3: downstream evaluation and release candidate

### PR RC-1: downstream evaluation

Begin only after MNT-4 and every accepted Phase 2 implementation have landed.
Evaluate the complete proposed stable surface in one substantial anonymized
downstream without naming private consumers. Exercise upgrade, maintenance
handles and flush points, dense and sparse residency, persistence, path
invalidation, worker-pool behavior, and accepted prototype behavior. Record
findings, fixes, and explicit deferrals.

Any accepted code fix lands before the RC snapshot and reruns its affected
evidence. A breaking finding returns to implementation; it is not deferred
through the compatibility freeze. A breaking finding in a surface published by
0.13 requires a new breaking minor release, an upgrade-guide amendment, and a
repeat of the downstream gate before any RC; do not contradict the "final
breaking release" claim by hiding that change in the candidate.

### PR RC-2: v1.0.0-rc.1 preparation

- add the immutable `compatibility/1.0.0-rc.1` snapshot only after the source
  surface is final;
- assemble release, decision, and optimization fragments, archiving before any
  assembled file exceeds 24,000 tokens;
- set the RC version and verify package metadata and portable assets;
- run release mode on the exact candidate SHA, including the complete platform,
  sanitizer, exception-free, no-RTTI, documentation, package, compatibility,
  and compiler-floor matrix; and
- run the archive fuzzer for 60 minutes under ASan/UBSan and commit every
  minimized regression input.

Tag only the exact successful SHA. A code fix requires a new RC and restarts
the observation window.

## Phase 4: observation and general availability

Observe the candidate for at least seven days. Then rerun release mode on the
same RC SHA. Do not substitute a later documentation commit for this
observation check.

For GA, clear the prerelease label on a separate commit, assemble any remaining
fragments, confirm there is no untriaged correctness, security,
performance-gate, or release-process incident, and run release mode again on
the exact GA commit. Preserve both the successful same-RC-SHA rerun and GA
evidence artifacts before tagging `v1.0.0`.
