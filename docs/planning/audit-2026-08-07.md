# Fourth Audit — 2026-08-07 (post-v0.12, `bd304e7`)

Full audit of tess at `origin/main` = `bd304e7`, three commits past the
`v0.12.0` tag. Six requested dimensions: adoption friction, performance,
documentation, API design, correctness, and CI speed/coverage trade-offs.

Method: seven parallel read-only discovery reviews, one per dimension
with correctness split across two (path/topology/storage/persistence and
sim/ops/ecs/gpu), each scoped to tracked files only, followed by a
single adversarial verification pass on a stronger model over the
assembled HIGH findings and the sharpest unverified claims. Findings
were deduplicated against `audit-2026-07-09.md`, `audit-2026-07-11.md`
and their remediation plans, the `#107` post-v0.12 corrections in
`docs/decisions/CHANGELOG.md`, `docs/planning/optimization-log.md`, and
`docs/tdd/v1-stabilization.md`.

Every finding marked **verified** below was re-read against source
during consolidation or by the verification pass; findings marked
**reported** rest on the discovery pass alone. The verification pass
refuted nothing and downgraded nothing, corrected three line references
in C3, and found API3 understated. Severity on three items was lowered
during consolidation — see API4, API14 and API17, where the reviewing
pass overstated a documented behaviour as a defect.

Verdict up front: one HIGH correctness defect (sparse residency erases
dirty marks it never observed), one MEDIUM correctness defect in the
newest movement tier (PIBT priority inheritance is missing a filter its
sibling paths have), and a cluster of gate-integrity problems where the
instrument is weaker than it appears — a ccache key collision that has
been silently cold-building the second-longest PR job, a whole
subsystem excluded from performance gating on a stated rationale that is
factually wrong for it, and two O(n^2) paths that no benchmark times.
Documentation and API design findings are dominated by 1.0-window items:
things that are free to change now and source-breaking after.

Severity: HIGH = act before 1.0 planning proceeds; MED = real defect or
real waste, schedule it; LOW = opportunistic.

## Correctness

### C1 [HIGH] Sparse eviction resets `ChunkMeta::version`, so a dirty observation can erase a mark it never saw — *verified*

`include/tess/storage/sparse_world.h:358` with
`include/tess/storage/chunk_meta.h:141-149`.

The reload path in `ensure_resident` assigns `metadata_[slot] =
ChunkMeta{}`, restarting `version` at 0, while the sibling
`slot_generation_[slot] = ++generation_clock_` correctly uses a
monotonic world-level clock. `meta_clear_dirty_observed` gates entirely
on `meta.version != observed.version`.

Trigger, capacity-1 sparse world: mark `K0` dirty (version 1); observe
it; load `K1`, evicting `K0`; reload `K0` (version back to 0); mark
`K0` dirty again (version 1 again); `clear_dirty_observed(K0, observed)`
now returns `true` and clears the flag. The contract at
`chunk_meta.h:36-39` requires `false` with the flag retained: "The clear
succeeds only if no later dirty mark changed the version, so a
maintenance pass cannot erase intervening marks."

Consequence: silent stale derived state. A maintenance pass erases a
dirty mark belonging to a different residency interval, so the chunk is
never rebuilt. The dense world reaches this only through 2^32
wraparound; sparse needs a single eviction.

The fix has an in-tree precedent: `route_cache.h:424-449` already folds
`residency_generation` into its fingerprint precisely because version
resets on reload. Either seed `metadata_[slot].version` from
`generation_clock_` on reload, or add the residency generation to
`DirtyObservation` and reject a mismatch. `DirtyObservation` should also
join the eviction-invalidation list at `sparse_world.h:160-163`.

No test covers it: `tests/tess_residency_test.cc:188-196` tests
staleness only within one residency interval, and no test in the
residency, sparse-stream, maintenance, or storage suites carries an
observation across an eviction.

### C2 [MED] PIBT priority inheritance moves terminal and goalless agents, and rewrites their state — *verified*

`include/tess/sim/pibt_movement.h:369-371`, against `:390-395` and
`:411`.

The top-level decision loop excludes agents that are finished or
unreachable:

```cpp
if (!agents[agent_index].has_goal ||
    agents[agent_index].phase == PathAgentPhase::Unreachable) {
  scratch.state[agent_index] = decided;
  continue;
}
```

The apply loop's stay-put branch at `:411` tests the same condition. The
priority-inheritance path gates on `scratch.state[occupant] == undecided`
alone, with no such filter, so a moving agent can displace an occupant
the other two paths agree is immovable. The off-route branch then
rewrites the displaced agent unconditionally: `status = NoPath`,
`phase = Blocked`, `blocked_retries = 0`.

Ordering makes this reachable rather than theoretical: `:166-174` forces
`elapsed = 0` for every inactive agent while active agents carry
`elapsed >= 1`, so the descending sort at `:181-190` always places
inactive agents *after* active ones — they are still `undecided` when
active agents decide.

Consequence: an `Unreachable` agent, documented at `path_agent.h:22-23`
as "terminal until a new goal is assigned", is resurrected into
`Blocked`, re-enters the retry budget, and on the next exhaustion calls
`fail_path_agent_flow` a second time for one admission. `counters.failed`
increments twice while `record_left_outstanding()` decrements once, so
`FlowCounters::retention_identity_holds()` (`diagnostics.h:465-468`)
becomes permanently false. Separately, arrived agents a caller treats as
static get shoved by passing traffic and counted in
`stats.frame.advanced`.

Fix: apply the same filter in `run_decision` — treat such an occupant as
immovable, claim its tile so later deciders are vertex-rejected rather
than stacking on it, and report failure to the inheriting parent so it
backtracks.

No test covers it. `tests/tess_pibt_movement_test.cc` builds peers
through `add_agent`, which sets `has_goal = true` and
`phase = Following`. The one test with inactive agents in the span
(`RingRegressionPibtSolvesWhereJointCongestionSeals`) masks it with a
consumer-side `SettledTag` recipe that makes arrived tiles impassable,
so `start_deciding` fails on `BlockedFrom` before enumerating.

### C3 [MED] Region-graph freshness observes only `topology_version`, so a raw field write can produce a definitive wrong `Unreachable` — *verified*

`include/tess/topology/topology.h:1773-1822`, consumed by
`include/tess/path/precheck.h:69-96` and acted on by
`include/tess/path/path_runtime.h:834-856`.

Three separable facts, each confirmed against source:

1. `is_region_graph_fresh` compares `local_topologies_[c].version()`
   against `world.meta(ChunkKey{c}).topology_version`, and
   `topology_version` is incremented only in `mark_topology_dirty` /
   `mark_topology_rebuilt` (`storage/world.h:242,246`,
   `storage/sparse_world.h:505,509`; `archive.h:730-733` deliberately
   preserves it on load). `World::field(coord)` (`world.h:351-357`)
   returns a bare mutable reference and touches no dirty or version
   machinery.
2. For the built-in `StairTransitions<Tag>` the provider stamps cannot
   compensate. It has no non-static data members, so
   `transition_provider_revision` returns a constant `0`
   (`transition_provider.h:90-99`) and
   `transition_provider_instance_identity` returns `nullptr`
   (`:107-116`). `matches_provider` (`topology.h:488-495`) compares
   exactly type identity, instance and revision, so for an empty
   provider it is a compile-time-constant match.
3. The conclusion follows to a real caller. `precheck_path`
   (`precheck.h:69-96`) returns `PrecheckStatus::Unreachable`, and
   `precheck_rules_out_path` is true only for that value (`:40-43`).
   `precheck_prepass` (`path_runtime.h:834-856`) then records
   `PathStatus::NoPath` and sets `processed_[i] = 1`, so the
   field-product grouping and the search loop skip it. A* never runs and
   nothing re-checks.

So a field write that opens a real route — a stair placement, a wall
demolition — leaves the graph reporting fresh and yields a definitive
wrong `NoPath`. `precheck.h:45-48` claims the opposite: "a graph that no
longer matches the world is GraphStale ... BEFORE calling reachable(),
because a stale graph can otherwise return a" wrong answer.

Scope: this needs the involved chunks resident. On a sparse world a
route through non-resident chunks degrades to `MissingChunk` and A* runs
anyway. On a dense world it is unconditional, and the stairs example in
`docs/use-cases.md` fits the shape exactly (see D3).

This is a documentation-and-contract fix more than a code fix: state the
obligation where the edit happens (`transition_provider.h:149-168`,
`docs/architecture/topology.md`, `docs/architecture/storage.md:219`) —
editing any field a movement class or its provider reads requires
`mark_topology_dirty` on the owning chunk — and soften `precheck.h`'s
claim to say the check detects version and residency changes only.

Worth noting that `use-cases.md` (D3 below) documents the stairs example
as flowing dirty state automatically, which is the misunderstanding this
finding describes.

### C4 [MED] `ensure_resident` with an out-of-shape key writes out of bounds in direct-slot mode — *verified*

`include/tess/storage/sparse_world.h:349-368` reaching `:69-73`.

`ChunkDirectory::insert`'s direct branch bounds-checks only through
`TESS_ASSERT(key.value < direct_slots_.size())` and then writes
unconditionally, while `find` at `:47-54` deliberately returns `npos`
for an out-of-range key. The read path is therefore safe and the write
path overflows: `find` returning `npos` falls through the
already-resident early-out into `acquire_slot()` and `insert()`.

Trigger in a release build: a 16-chunk shape with a 16-page budget takes
the direct branch, and `ensure_resident(ChunkKey{16})` writes
`direct_slots_[16]`.

Qualifier: `ensure_resident`'s Doxygen at `:347` does document the
precondition ("`key` is inside the bounded shape; debug builds assert
otherwise"), so this is an unchecked documented precondition, the same
class as C1 in the 2026-07-11 audit, not an undocumented bug. It is
raised to MEDIUM because `ensure_resident` is the only residency entry
point and has no checked counterpart, unlike `chunk()`, `meta()` and
`resolve()`.

Fix: return an invalid `ResidencyHandle{}` when `!contains(key)`, or add
`try_ensure_resident`.

### C5-C11 [LOW] — *reported unless noted*

- **C5 (verified).** PIBT fires a spurious arrival for a goalless agent
  displaced onto the origin (`pibt_movement.h:449-457`).
  `clear_path_agent_goal` zeroes `goal`, so a goalless agent pushed onto
  `(0,0,0)` compares equal. `arrive_path_agent` then increments
  `completed` and calls `record_left_outstanding()` for an admission
  that never happened. Every other arrival site reaches the check behind
  an explicit `has_goal` gate; PIBT is the exception. Same root as C2.
- **C6.** `for_each_dependency_chunk` emits an out-of-range `ChunkKey`
  for an out-of-world `from` (`topology/transition_model.h:440-442`),
  while `for_each_reverse` guards at `:420`. The consumer at
  `field_product_cache.h:673-683` indexes `seen[]` with it unchecked.
  Latent — the only in-tree caller passes in-world tiles.
- **C7.** Sparse `dirty_chunk_domain` / `active_chunk_domain` yield
  residency-ordered keys (`sparse_world.h:759-766`), a function of
  load/evict history, while the dense counterpart iterates ascending and
  `explicit_chunk_domain` sorts. `block.h:187` calls `ChunkDomain` an
  "ordered view" and `docs/architecture/block.md:131` guarantees
  "Iteration is deterministic when domains are produced by the provided
  builders." Non-commutative block kernels can therefore differ run to
  run on identical sparse content. `tests/tess_residency_test.cc:334-337`
  sorts before comparing, so the instability is known but the builder
  contract is untested.
- **C8.** `EventStream::retire_batch` decrements outstanding inventory
  directly (`event_stream.h:184`) where every other terminalization site
  routes through the zero-floored `record_left_outstanding()`. Any state
  with `outstanding_current < events_.size()` wraps the unsigned counter.
  Corrupts diagnostics, not simulation.
- **C9.** A* fast-path route costs add two already-clamped `uint32`
  distances without saturation (`detail/astar.h:260-261, 368-369, 583,
  969`) where `best_chunk_portal` uses `saturating_add`. Requires a
  >2^32-tile dense world; not constructible. Same symmetry argument as
  C3 in the 2026-07-11 audit, at different sites.
- **C10.** `save_world_archive` writes `lattice_version` at a
  compiler-deduced width (`persistence/archive.h:808-809`) while the
  identity on the line above is explicitly `uint32_t` and the reader is
  fixed-width. A custom lattice with a `uint64_t` version saves `Ok` and
  can never be loaded. Unreachable with both shipped lattices; flagged
  because the lattice slot is a documented extension point.
- **C11.** Provider chunk-ownership is assert-only
  (`topology/topology.h:1044-1050`); under `NDEBUG` a violating provider
  leaks portals unboundedly, because `std::erase_if` keys removal on
  `portal.from.chunk` while `append_provider_portals` re-appends every
  update. Contract is documented at `transition_provider.h:26-35`, so
  this is a hardening gap. Skipping rather than asserting would bound it.
- **C12 (unverified).** `DeltaCollector`'s coalescing table derives its
  slot count from the requested `entity_capacity` rather than the
  realized `pending_entities_.capacity()` (`sim/delta_frame.h:249-255`),
  and both probe loops are unbounded. On a `vector` whose `reserve`
  over-allocates past `2 * entity_capacity`, the table can fill and the
  probes spin forever. Not reproducible on libstdc++, libc++ or MSVC,
  all of which allocate exactly. Cheap to make unconditional by deriving
  the slot count from the realized capacity.

## Performance

Two O(n^2) paths that no benchmark times, and a cluster of gaps where
the benchmark that carries a behaviour's name measures a degenerate case
of it.

### P1 [HIGH] Queued-op planning is O(n^2) in operations per frame and no benchmark times it — *verified*

`include/tess/ops/queued.h:1809` and `:1623-1636`, plus the phase
grouper at `:1894-1900`.

`plan_operations` calls `detail::find_hazard(report.plan().operations(),
planned)` once per operation, and `find_hazard` scans every previously
accepted operation running `chunks_overlap` on each pair.
`plan_parallel_execution_phases` then compares each operation against
every member of the current phase; in the all-disjoint case the phase
grows to n, so that loop is quadratic too.

Every benchmark plans *outside* its timed region
(`bench/parallel_phase_support.h:117-119`, `bench/tess_bench.cc:760`,
`:787`), and the one in-loop planner call
(`bench/tess_scheduler_bench.cc:191`) plans exactly one operation. So a
consumer enqueuing per-chunk operations pays roughly n^2/2 hazard checks
per frame — 256 chunks is ~33k pair checks, 4096 chunks is ~8.4M — and
no gate, sentinel, or counter golden would move if that cost changed by
any factor.

Fix: add a gated benchmark timing `plan_operations` plus
`plan_parallel_execution_phases` at two operation counts (256 and 4096)
so the quadratic shows as a shape rather than a point. Independently,
index accepted operations by chunk key so hazard detection is O(sum of
chunk lists). Note that the 2026-07-11 audit's M4 explicitly *deferred*
the hazard-scan complexity by decision; what is new here is that the
cost is also unmeasured, so the deferral cannot be revisited on evidence.

### P2 [HIGH] `FieldProductCache` eviction is O(entries) per evicted entry, and both its benchmarks hold at most three — *verified*

`include/tess/path/field_product_cache.h:596-607`;
`bench/tess_path_product_bench.cc:481`; `bench/tess_fields_bench.cc:228`.

`evict_to_budget` runs a full linear min-scan of `entries_` per eviction.
The benchmark named `path/field_product_cache_lru_eviction_512x512` sets
`reserve_entries(2)` and stores two products; `fields/cache_eviction`
cycles three keys through a two-product budget.

This is the same defect the 2026-07-12 optimization-log entry
"Intrusive LRU + ECS Hash/Lookup Cuts" already fixed for sparse
residency — 400 ns to 114 ns, 3.5x — and that win was only visible
because `eviction_churn_512` cycles 512 entries. `FieldProductCache` was
never converted and has no equivalent benchmark, so the benchmark
carrying "LRU eviction" in its name measures the two-entry degenerate
case and an eviction-policy regression is undetectable.

Fix: mirror the residency intrusive LRU list, or at minimum add a
many-entry eviction-churn benchmark before touching the policy.

### P3 [MED] The runtime's field-product path reallocates world-sized storage on every rebuild — *verified*

`include/tess/path/path_runtime.h:802-803` and `:589-591`.

`store(std::move(unit_field_product_))` move-constructs into the cache,
stealing `distance_`, `goals_` and `dependencies_`. The member is left
at zero capacity, so the next `build_distance_field_product` runs
`distance_.assign(node_count, infinite_distance)` against an empty
vector — a fresh `node_count * 4`-byte allocation. On a 512x512 world
that is roughly 1 MiB per rebuild, plus the dependency vector, on every
world edit, cache eviction, or provider revision change.
`reserve_unit_field_product_nodes()` therefore only helps the first
build.

The comment at `:799-801` argues only that the moved-from state is never
*observed*; the capacity loss is not mentioned. `fields/build_alloc_gate`
never stores into a cache, so no allocation gate covers this path.

Fix: have `store*` return the stored pointer and swap the caller's
emptied product back with the cache's previous buffers; add an
allocation gate over the runtime field-product build.

### P4 [MED] Store-then-relookup runs a redundant O(entries) scan and inflates the published cache-hit counter — *verified*

`include/tess/path/path_runtime.h:802-806`;
`include/tess/path/field_product_cache.h:332-350`.

The runtime does `(void)cache.store(std::move(product)); product =
cache.lookup(...)` purely to recover a pointer the store already had.
`lookup` walks `entries_` calling `key_matches_class`, which
reconstructs `const auto model = Model{provider};` *inside* the loop and
compares thirteen fields plus a `std::equal` over the goals vector.

Beyond the wasted scan, `lookup` increments `hits_` at `:344`. So every
miss-then-build records a spurious hit, and the cache-hit-rate counters
that `record_field_product_cache_counters` publishes as benchmark
evidence read one hit too high on every build. That half is a reporting
defect, not a performance one.

Fix: return `const DistanceFieldProduct*` from `store_with_key`; hoist
the `Model` construction and world-derived constants out of the loop.

### P5 [MED] The whole `fields/` family runs on a 64x64 world — *reported*

`bench/tess_fields_bench.cc:26-32` uses
`Shape<Extent3{64,64,1}, Extent3{8,8,1}>`, 4,096 tiles. Distance array,
generation array and product copy are 16 KiB each: the entire working
set is L1/L2 resident. The 2026-08-02 bare-metal campaign independently
measured this family at 0.001-0.007 LLC MPKI.

So the loosest ceilings in the suite (850 us to 1.1 ms against ~124-151
us observed) sit on the least representative workload, and any change to
`DistanceFieldProduct` layout, per-build `assign` cost, or
dependency-capture locality is measured only where everything fits in
cache. The precedent is exact: the 256-chunk
`storage/world_dirty_chunks_iteration` was flat at 125 ns both ways
until the `_16k` variant existed.

This is distinct from the known ceiling-recalibration item — the
*ceiling value* is deliberate and tracked; the *workload dimension* is
not. Fix: add one 512x512 variant so the family has both a
cache-resident and a memory-bound point.

### P6-P9 [MED] — *reported*

- **P6.** Worker-pool dispatch takes `mutex_` twice per worker per phase
  (`ops/phase_executor.h:550`, `:587-591`): once to read the job
  descriptor, again to decrement `active_workers_`, and the dispatcher's
  `done_cv_` predicate cannot be satisfied until the last worker
  completes the second acquisition. 2N serialized critical sections per
  dispatch, growing linearly with worker count. The 2026-07-12 M8 work
  fixed counter false sharing, run claiming and wakeup storms but did not
  touch the handshake, and its A/B ran at w4 where 8 acquisitions are
  noise. Consistent with the 2026-08-04 campaign's unexplained "beyond
  24 workers nothing improved" plateau, though not proven to be its
  cause — settled by A/B-ing an atomic decrement plus last-worker notify
  at widths 4/24/96.
- **P7.** `results_` false-shares whenever a phase has fewer than
  4x worker_count operations (`phase_executor.h:475-476`).
  `job_stride_ = max(1, count / (workers * 4))` with 16-byte
  `PlannedExecutionResult`, so stride-1 runs land 4-8 to a cache line —
  exactly the small-phase/wide-pool regime where the pool already loses.
  The gated `parallel/*` family (256 chunks, w2/w4) has stride 16-32 and
  never enters it. M8 applied `alignas(128)` to the two hot counters for
  this reason and left `results_` unpadded. Bears on the open
  high-width noise item. The dispatcher only reads the first
  non-`Executed` result (`:538-542`), so per-operation results are not
  actually required.
- **P8.** `resolve_local_coordination` inserts into a sorted vector
  (`spatial/local_coordination.h:236-238`), so R reservations cost
  O(R^2) element moves — at 1,000 reservations roughly 500k `Coord3`
  moves already inside the measured 347 us. The suite has exactly one
  spatial benchmark at one fixed size, so a constant-factor regression
  and an exponent change are indistinguishable. The optimization log's
  recorded retry condition is keyed on *option* counts; the quadratic
  term is in the *reservation* count, so the trigger does not cover it.
- **P9.** `collect_render_tile_deltas` runs a full chunk sweep per
  scheduler tick regardless of dirty count (`sim/render_delta.h:100-119`)
  and has no benchmark. The `render_delta/*` family exercises a
  different collector in `sim/delta_frame.h`. The O(chunk_count) floor
  itself is the recorded M5 design-level backlog item; the coverage gap
  on this entry point is not.

### P10-P15 [LOW] — *reported*

- **P10.** The sentinel mapped to `include/tess/sim/`
  (`parallel/tile_touch_scoped_threads_w4`) measures thread creation —
  45x its serial control, and the widest interval of the twelve
  sentinels in the 2026-08-04 paired run. `parallel/chunk_compute_pool_w4`
  is the compute-bound alternative.
- **P11.** `PathScratch::parent_` is 8 bytes per node written on every
  relax (`path/path.h:718`), 2 MiB on a 512x512 world, read only during
  reconstruction. Narrowing is a different change from the rejected
  interleaving experiment — that entry credited packing — but the
  element type must follow `ShapeTraits<Shape>::TileKeyStorage`.
- **P12.** `grow_suffix_index` copies the whole slot table before
  reassigning it (`path/route_cache.h:366`); `std::move` suffices.
- **P13.** Corridor chunk dedup is O(corridor^2)
  (`topology/topology.h:1711-1717`). Negligible at the gated size, and
  no longer route is gated.
- **P14.** Nanosecond-floor gates on residency admit 12-25x drift, and
  the log records drift already happening at +25.0% seen by neither
  instrument. A documented, reasoned tradeoff; recorded because the gap
  is now demonstrated rather than hypothetical.
- **P15.** `docs/assets/benchmark-trends.svg` is stale by ~4 weeks and
  two regression/fix events. See D5, which is the same artifact.

Coverage gaps with no benchmark at all: `plan_operations` /
`plan_parallel_execution_phases` at n>1; `collect_render_tile_deltas`;
`spatial/tactical_assignment.h`'s `assign_tactical`; `FieldProductCache`
above three entries; `WeightedPortalSegmentCache` at budget (already
open per the 2026-08-06 log entry).

## CI

### CI1 [HIGH] `ccache` restore-keys collide across presets — *verified*

`.github/workflows/ci.yml:84-85`, same pattern at `:577-578`.

```yaml
key: ccache-dev-${{ github.sha }}
restore-keys: ccache-dev-
```

GitHub restore-keys match by prefix, so `ccache-dev-` also matches
`ccache-dev-asan-*`, `ccache-dev-tsan-*`, `ccache-dev-werror-*`,
`ccache-dev-cppcheck-*` and `ccache-dev-clang-tidy-*` — all real
namespaces, created by the `quality` matrix at `:426-427` from the
preset list at `:398-400` — returning the most recently created.
`ccache-macos-dev-` is likewise a prefix of `ccache-macos-dev-asan-`.

The collision is provable from the tracked files alone. It was
additionally observed live during this audit: a job keyed
`ccache-dev-<sha>` logged `Cache restored from key:
ccache-dev-cppcheck-<sha>`. That observation came from a workflow run
log rather than the repository, so re-confirm it before acting.

`dev` is the second-longest PR job at ~10.2 min, of which the build step
is ~80%. When the restore lands on a sanitizer preset, essentially every
object misses and the build is cold — then the foreign objects are saved
back into the `dev` namespace, which is why the ambiguous namespaces run
3-10x larger per entry than the unambiguous ones.

Fix: make each namespace terminal — `ccache-dev--${{ github.sha }}` with
`restore-keys: ccache-dev--`, or move the discriminator to a segment
that cannot be extended. Apply to `dev`, `macos`, and audit
`ccache-bench-`, which `paired-bench` uses as a deliberate fallback.

### CI2 [HIGH] `include/tess/ops/` is excluded from performance gating on a rationale that is wrong for it — *verified*

## API design

The single most useful framing here: nearly every item below is free to
fix now and source-breaking after 1.0. That makes the 0.13 window
described in `v1-stabilization.md:298-308` the natural home for most of
them.

### API1 [HIGH] `save_world_archive`'s status channel is dead — *verified*

`include/tess/persistence/archive.h:763-849`. The function assigns only
`result.info.*` and `result.bytes_processed`; `result.status` is never
written, so it is invariantly `Ok` — while the shared
`WorldArchiveResult` advertises the full 14-value `WorldArchiveStatus`
enum and the comment at `:108` presents it as "shared by archive
inspection, saving, and loading".

A caller writing symmetric error handling writes dead code, and — worse
— infers that save has a failure channel and therefore does not guard
the real failure mode: unbounded `std::vector` growth at `:772-793`,
which throws `bad_alloc` or falls outside the contract entirely in an
exception-free build.

Fix: give save its own result type without `status`, or document at the
declaration that save's status is invariantly `Ok`. The former is
source-breaking and honest.

### API2 [HIGH] `tess::detail` types appear in public signatures, members and documented aliases — *reported*

`experimental/maintenance.h:547,550` (`FifoScheduler` and
`CoalescingScheduler` are aliases of `detail::QueuedScheduler`);
`sim/pibt_movement.h:90,133` (`PibtPriorities::frames` is
`std::vector<detail::PibtFrame>`; the `detail::PibtRanking` concept
decides whether a user's ranking lambda is accepted and is unnameable by
contract); `ops/queued.h:1195-1197` (`dirty_partitions()` returns
`std::span<const detail::PhaseDirtyPartition>`); `core/shape.h:367,378`
(`TileKey::value` is `detail::UInt128` for any shape needing >64
tile-key bits, and `core/uint128.h` is an implementation header with a
deliberately partial operator set).

All of these are listed in `docs/architecture/surface.json` — promised
stable — while `docs/style.md` declares `detail` carries no
source-compatibility guarantee. The two promises contradict, and 1.0
would freeze a `detail` layout either way.

### API3 [HIGH] Value-returning builders hand out spans that dangle at end of full-expression — *verified in part*

`block/block.h:222-233` with `:258`; `ops/queued.h:1856-1858`;
`sim/delta_frame.h:143-149,398,427`.

`block.h:258` deliberately deletes `chunk_domain(OwnedChunkDomain&&)` to
reject a borrowed domain whose owner would be a temporary — but the
three factories all return by value, and
`explicit_chunk_domain(keys).view()` / `.keys()` / `.begin()` all
compile, yielding a span into a vector destroyed immediately. The
deleted overload makes this worse rather than better: a user who hits
its error will "fix" it by adding `.view()`.

Same shape in `queued.h`: `plan_operations` returns `ExecutionReport` by
value (`:1856-1858`), `.plan()` returns a reference into that temporary
(`:1275-1277`), and `operations()` returns a span over its member vector
(`:565-568`) — so the idiomatic `for (const auto& op :
plan_operations(world, ops).plan().operations())` iterates freed memory.
`ExecutionPhase` *is* protected by a generation check (`:639`, with a
deliberate `bump_generation()` on assignment at `:586-608`), so the
unprotected accessors read as safe by comparison.

`DeltaFrame` is a copyable struct of five spans (`delta_frame.h:143-149`)
into collector-owned vectors that `publish()` swaps (`:427-431`). Holding
last frame's `DeltaFrame` across a `publish()` — the natural
double-buffering move — is worse than reading the previous buffer: the
held spans alias the vectors that become the *pending* accumulator,
which is immediately cleared and refilled by subsequent `record_*`
calls. The caller reads torn mid-tick data, and because the storage is
live and owned throughout, no sanitizer will flag it.

`PathView` (`path/path_view.h:30-38`) shows the project already knows
the fix; it simply is not applied here. Fix: `&&`-delete the observers,
and make `DeltaFrame` move-only with a collector version re-check.
Source-breaking only for code that is already dangling.

  and therefore outlive the corresponding sinks", but `TraceRecord::label`
  is a `std::string_view` and `panels.h:147` dereferences it — so a
  dynamically built label handed to a render thread is a dangling read
  the header promised was safe.
- **API17.** Duplicate names: `to_frontier` is a verbatim four-overload
  alias of `collect_into`; `TraceBuffer::stats(category)` and
  `TimingSnapshot::category(category)` do the same job under opposite
  names. `EventStream::clear` and `discard_all` have identical bodies —
  but, contrary to the reviewing pass, `event_stream.h:80-85` *does*
  disclose this ("With flow accounting attached this conservatively
  counts the discarded batch as dropped after admission; consumers that
  read the batch should prefer `consume_all`"), so that pair is
  redundant naming, not a defect.
- **API18.** `tag_identity` is the RTTI-free identity mechanism and
  silently breaks across a DSO boundary — with `-fvisibility=hidden`, a
  region graph built in a shared library reports `GraphStale` forever.
  `docs/integration-policy.md` states the limit honestly, but nothing on
  the affected public types signals it. Decide before 1.0 whether
  cross-DSO use is supported.

**Clean:** every header has `#pragma once`; all 16 macros carry the
`TESS_` prefix; self-containment is CMake-enforced in both exception
modes and both include orders, with the header list kept in sync with
the filesystem in both directions; no non-inline namespace-scope
variable exists anywhere; every optional-dependency header gates on a
`TESS_ENABLE_*` macro *and* `#error`s when the third-party header is
missing; no `get_`-prefixed accessor exists; `PathView` correctly
deletes both rvalue-vector constructors.

## Adoption friction

### AD1 [MED] A bare top-level configure fetches GoogleTest, and the installation page says it does not — *verified*

`CMakeLists.txt:41` defaults `TESS_BUILD_TESTING` to
`PROJECT_IS_TOP_LEVEL`; `:359-376` gates `add_subdirectory(tests)` on it
plus `BUILD_TESTING`, which `include(CTest)` defaults ON; and
`tests/CMakeLists.txt:4` calls `tess_require_googletest()`, a
configure-time `git clone`. No preset is involved.

`docs/packaging.md:5-7` states: "GoogleTest, Google Benchmark, EnTT, and
Flecs are development or optional integration dependencies fetched only
by developer presets."

So an evaluator clones the repo, types `cmake -B build`, and on a
corporate network or offline laptop gets a failure inside a GoogleTest
clone they never asked for — having just read that this would not
happen. Fix: correct the sentence to name the options rather than the
presets, and point evaluators at the fetch-free `examples` preset.

### AD2 [MED] Three documents state three different include-surface policies — *verified*

`docs/for-agents.md:44-47` says "Consume only `<tess/pathfinding.h>`,
`<tess/simulation.h>`, or the `<tess/tess.h>` umbrella … and
`tools/check_public_surface.py` enforces it."
`docs/packaging.md:69-70` says the opposite: "In compile-sensitive code,
prefer the narrowest public header that owns the API." The quickstart in
both `README.md:39` and `docs/index.md:31` opens with a fourth header,
`<tess/core/config.h>`. And the cited tool enforces neither policy — it
verifies that each name appears in `surface.json`, across all installed
headers.

A developer, or the coding agent `for-agents.md` is explicitly written
for, cannot tell which headers are safe to depend on. Fix: pick one
policy, state it once, and drop or correct the enforcement claim.

### AD3 [MED] The WebGPU example is built and browser-tested by CI but reachable from nothing an adopter reads — *verified*

`examples/webgpu_compute/webgpu_compute.cc` is compiled by
`tools/build_web_demo.sh:84-98` and checked live by
`.github/workflows/pages.yml:155`, but has no `add_executable` in
`examples/CMakeLists.txt`, no entry in `docs/examples.md`, and no
mention in `docs/architecture/gpu.md` — which offers three sentences of
prose for the feature most likely to need a worked example, since it
requires a consumer-supplied device, queue and 4-byte-aligned buffer
discipline. A grep of `docs/` finds `demo/` and `demo/colony/` but never
`demo/webgpu/`.

Fix: catalog it, link the live page from `gpu.md`, and note that it
builds only under Emscripten.

### AD4-AD9 [LOW] — *reported*

- **AD4.** `README.md:150` claims "Every example is annotated in the
  example catalog" — `examples/documentation.cc` is not — and
  `docs/examples.md:3` claims examples build as `tess_<name>`, which the
  two web demos do not (`tess_web_colony_model`).
- **AD5.** The changelog jumps 0.4.0 to 0.12.0 with no explanation. The
  releases confirm nothing is missing, but an adopter doing diligence
  sees eight minor versions vanish in sixteen days and reads it as a
  truncated history — at exactly the trust decision point for a pre-1.0
  library. One sentence fixes it.
- **AD6.** Optional integration headers compile to nothing when their
  gate macro is absent, with no diagnostic. The inverse mistake is
  handled well (`#error` when the gate is on and the third-party header
  is missing). The behaviour is deliberate and should stay; the fix is
  documentation — the `target_compile_definitions` line appears only in
  `architecture/ecs.md:91`, not in packaging's include-surface section.
- **AD7.** The only documented route to the ECS adapter examples is the
  `dev` preset, which clones three dependencies and builds the entire
  Debug test suite — ten minutes and three clones to run one 132-line
  example.
- **AD8.** `docs/dependencies.md` is in `exclude_docs` and linked only
  from another excluded page, so a reviewer doing supply-chain diligence
  on the published site cannot find the pinned versions at all.
- **AD9.** `getting-started.md` names example files as code spans rather
  than links, eight times, on the single most important adoption page —
  while `docs/examples.md:69-81` already maintains the link-reference
  block.

**Clean:** every preset named in any doc exists and parses, and the
documented binary paths match; version `0.12.0` agrees across
`cmake/tess-version.cmake`, `ports/tess/vcpkg.json`, `conanfile.py`,
README, index, packaging, the changelog and the newest tag, gated by
`tools/check_doc_versions.py`; the C++20 / CMake 3.25 baseline is stated
identically everywhere and actually enforced; the install path is
complete and exercised end to end by `tools/install_smoke.sh` and
`tests/install_consumer/`, with the subproject-defaults-off contract
asserted by the FetchContent fixture; EnTT, Flecs, ImGui and WebGPU are
genuinely optional and SHA-pinned; every example self-checks before a
nonzero exit and CI runs all of them.

## Suggested remediation order

1. **C1** — the only HIGH correctness defect, and it silently drops
   work rather than failing loudly. **C2/C5** next: they are one root
   cause in the newest movement tier, and PIBT is what the movement arc
   closed on.
2. **CI1, CI2, CI14** together — the gates are the instrument every
   later claim is measured against, and two of them are currently
   weaker than they read. CI14 is one line per job and is what would
   have caught CI1. Same logic the 2026-07-11 audit used in putting
   bench integrity first.
3. **P1, P2** — two O(n^2) paths that no benchmark times. Add the
   measurements before the fixes, so the fixes have before/after
   evidence, per the standing rule in the remediation protocol.
4. **D1, AD1, AD2** — the three places where a doc actively tells a
   reader something false, all on first-contact pages.
5. **API1, API2, API3** and the 0.13-window items (API4-API13) —
   naturally folded into the v1-stabilization §12.1 breaking-change
   window rather than run as a separate workstream.
6. **CI8** for PR latency once CI1 lands, then CI3-CI11 opportunistically.
7. Remaining LOWs alongside whichever subsystem is next touched.
